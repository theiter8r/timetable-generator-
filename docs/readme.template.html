The problem

One teacher, two rooms, same hour

A department timetable falls apart on a single failure: Prof. Kale is down to teach SE-B at Monday 09:00 and SE-C at Monday 09:00. Everything else can be right and the timetable is still unusable.

This is not treated as something to check for afterwards. It is written into the model as a constraint, which means the left-hand state below is not a bug the solver might produce on a bad day — it is not in the space of answers it can return at all.

× Cannot be returned
Mon 09:00SE-B · DBMS · Kale
Mon 09:00SE-C · DBMS · Kale

Both sessions land on the same (teacher, slot) pair. Their sum would be 2, and the constraint caps it at 1.

✓ What it returns
Mon 09:00SE-B · DBMS · Kale
Mon 10:00SE-C · DBMS · Kale

Or it reports that no clash-free timetable exists and names what is blocking it. There is no third outcome.

The scheduling is done by OR-Tools CP-SAT, a constraint solver. No language model is involved in generating a timetable.

Getting started

Running it

uv sync
uv run timetable serve          # http://localhost:8000

On first run the configuration is seeded from a realistic sample department — six divisions, eighteen batches, twenty-two teachers, eighty-four teaching commitments — so there is something to generate before you have typed anything in. 

uv run timetable validate                 # pre-flight checks only
uv run timetable solve                    # solve and print a report
uv run timetable solve --out sheets.html  # ...and write every timetable
uv run timetable reset                    # restore the sample dataset
uv run pytest                             # the test suite

You allocate the teachers. The solver decides only when each session happens and which room it happens in.

Breaks carry real weight. They split the day into morning and afternoon — which is what “after the break” means when a teacher states a preference — and a two-slot practical can never be placed across one.

The model

Guaranteed, and merely preferred

Every rule in the first list is a hard constraint. They hold in any timetable the app produces, without exception, because a schedule that broke one would not satisfy the model. The second list is optimised only after all of the first already holds.

Always true

  • No teacher is in two places at once — across every year and division, which is the case at the top of this page.
  • No group of students is in two places at once. A division's lecture blocks all of its batches; sibling batches may still run practicals in parallel.
  • No room hosts two sessions at once, and a practical only lands in a room of the right type and capacity.
  • A two-slot practical occupies genuinely back-to-back slots on one day, never split by a break.
  • Days off and blocked slots are never used.
  • Every commitment gets exactly the sessions you asked for.

Optimised where possible

  • Morning or after-break preference, scaled by how strongly each teacher holds it.
  • An even weekly spread of a batch's classes rather than three of them stacked on a Tuesday.
  • No gaps in a student's day — an idle hour wedged between two classes.
hard — guaranteed soft — weighted, tunable

On the sample department the solver places all 144 sessions optimally in about four seconds and honours 95% of stated teacher preferences.

Failure

When it cannot be done

A bare INFEASIBLE is useless to whoever has to fix the timetable, so an impossible configuration is diagnosed rather than merely rejected.

Pre-flight checks run before the solver and catch most real misconfigurations by name — including bounds that are genuinely hard to see by eye:

Reported, not guessed 18 parallel lab blocks are required but at most 12 fit: 5 computer_lab rooms let only 1 division run practicals at a time, and the week has 12 non-overlapping 2-slot blocks (12 × 1 = 12).

That one is worth reading twice. Three batches per division means a single lab block consumes three rooms at once, and a day split by lunch offers only two non-overlapping double periods — so the ceiling has nothing to do with total lab hours. Without the check it surfaces as an unexplained failure.

If a configuration is still infeasible, the model is re-solved with the session-count requirement softened. You get the closest timetable that exists, plus a per-assignment account of what could not be placed and why.

Under the hood

How the model is built

One boolean per (commitment, possible start slot) says a session begins there, and one per (commitment, start, room) says which room it uses. Placements that would break contiguity, land on a day off or collide with a pinned event are never given a variable at all — so those rules hold by construction, and the model stays small.

The clash rules are then just capacity: for each teacher, each batch and each room, the sessions covering any one slot must sum to at most one.

The student rule is stated per batch rather than per division, and that single choice yields all three required behaviours at once — a division's lecture blocks every batch beneath it, two practicals for one batch conflict, and sibling batches remain free to run different labs in the same hour.

Verification

Checked, not asserted

views.audit() re-examines a finished timetable for clashes independently of the solver. It walks the returned sessions and looks for any teacher, batch or room occupying a slot twice, any practical broken across a break, and any session sitting on a blocked slot.

That is what the green Verified clash-free badge in the interface reports — a second opinion, not the solver vouching for itself. The test suite runs the same function, including a fixture built specifically to tempt the solver into the SE-B / SE-C overlap in a two-slot week where the only honest answer separates them.

Typography

Set in Anthropic Serif

Both optical cuts are used for what they were drawn for. Display — the tighter, higher-contrast cut — carries the headings and the large figures at the top of this page, in Light where the numerals run big enough to need the air. Text, more open and sturdier at reading size, sets everything you are reading now.

The application interface inverts that balance deliberately: serif for display moments only, and a system sans for the configuration tables, where a dense grid of inputs scans faster and a display cut would turn fragile.
